## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

RAG có thể tiếp tục trả lời khi dữ liệu thiếu, trùng, cũ hoặc nhiễu. Vì vậy cần một gate máy đọc được để chặn silent failure, đồng thời cần benchmark cố định để định lượng tác động lên retrieval và câu trả lời.

### Cách triển khai

Quality Gate tạo GX ephemeral context bằng API 1.x, đăng ký Pandas dataframe asset và chạy bốn loại expectation: row count, not-null, uniqueness và string length. Chuỗi rỗng ở trường bắt buộc được chuyển sang NA trước validation. Freshness tính tỷ lệ `age_days > 180` và FAIL nếu vượt 25%. Test set chọn deterministically từ clean data, có `id`, `type`, `question`, `ground_truth` và DOI ground truth. Evaluation tính retrieval hit, token-level F1 và judge; report tổng hợp số liệu thay vì hardcode.

### Input, output và contract

| Thành phần | Mô tả |
|---|---|
| Input | Clean/corrupted/repaired dataframe, Chroma index, shared test set |
| Output | Quality/freshness JSON, metrics/answers JSON, Markdown reports |
| Module phụ thuộc | Cleaning schema, retrieval QA |
| Module sử dụng output | Pipeline gate, corruption comparison, báo cáo nộp bài |
| Điều kiện lỗi | Thiếu cột, null/rỗng, duplicate DOI, summary ngắn, stale ratio >25% |

### Cách xác minh

```bash
python -c "from core.config import load_settings; from observability.quality import run_data_quality_checks; import pandas as pd; s=load_settings(); r=run_data_quality_checks(pd.read_json(s.paths.clean_json),s,'test'); print(r['success'])"
```

- **Kết quả mong đợi:** Baseline `True`; corrupted `False`; repaired `True`.
- **Kết quả thực tế:** Đúng chuỗi `PASS → FAIL → PASS`.
- **Artifact/log:** `data/quality/`, `data/results/*metrics.json`, `data/reports/`.

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Metric giữa ba trạng thái chỉ có ý nghĩa khi cùng câu hỏi và ground truth.
- **Các phương án:** Sinh test set mới mỗi lần; hoặc tạo một test set cố định từ baseline và tái sử dụng.
- **Phương án chọn:** Lưu cố định `data/eval/test_set.json` và dùng cho cả ba trạng thái.
- **Lý do:** Loại bỏ biến thiên do đổi đề, giúp delta metric phản ánh corruption/repair.
- **Bằng chứng:** Baseline và repaired đều đạt 1.0, trong khi corrupted giảm hit rate còn 0.6 và F1 còn 0.4 trên cùng 5 câu.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng:** Cú pháp `context.sources.pandas_default` của GX cũ không tồn tại trên Great Expectations 1.x.
- **Bước tái hiện:** Chạy quality checkpoint với API cũ trên GX 1.23.1.
- **Nguyên nhân gốc:** Breaking API change giữa các thế hệ Great Expectations.
- **Cách xử lý:** Dùng `gx.get_context(mode='ephemeral')`, `context.data_sources.add_pandas`, dataframe asset và whole-dataframe batch definition.
- **Cách xác minh:** Cả 6 expectation instances chạy; baseline success `True`, corrupted phát hiện uniqueness/summary failures.
- **Điều học được:** Cần bám đúng API version và kiểm tra report chi tiết, không chỉ nhìn process exit code.

## 7. Hiểu biết về luồng end-to-end

Crossref được lưu raw, parse và clean thành schema ổn định. Trước indexing, GX kiểm tra số dòng, completeness, uniqueness và summary; freshness kiểm tra tuổi dữ liệu độc lập với schema. MiniLM tạo vector và Chroma phục vụ truy vấn. Test set giữ DOI ground truth để Hit Rate đo retrieval, còn ground-truth answer dùng cho Token F1/judge. Nếu đổi test set giữa các trạng thái thì delta không còn phản ánh corruption. Repair được coi là thành công khi repaired Quality/Freshness PASS/FRESH và cả retrieval lẫn answer metrics quay lại baseline.

## 8. Phân tích kết quả

| Metric/signal | Baseline | Corrupted | Repaired | Nhận xét |
|---|---:|---:|---:|---|
| `retrieval_hit_rate` | 1.0 | 0.6 | 1.0 | Giảm 40 điểm phần trăm rồi phục hồi |
| `mean_token_f1` | 1.0 | 0.4 | 1.0 | Answer quality nhạy hơn retrieval |
| `judge_accuracy` | 1.0 | 0.4 | 1.0 | Judge hiện là fallback heuristic |
| `mean_judge_score` | 5.0 | 2.6 | 5.0 | Giảm 2.4 điểm khi corrupted |
| Quality Gate | PASS | FAIL | PASS | Phát hiện duplicate và blank summary |
| Freshness | FRESH | STALE | FRESH | 4.17% → 33.33% → 4.17% |

1. Duplicate/blank/stale corruption → GX uniqueness/length và freshness FAIL → Hit Rate/F1/judge cùng giảm.
2. Repair từ raw → mọi expectation và freshness phục hồi → toàn bộ metrics về đúng baseline.

Freshness thay đổi rõ nhất ở signal quan sát được, còn summary/title/noise làm Token F1 giảm mạnh nhất. Kết quả khác kỳ vọng đơn giản là row count vẫn PASS ở corrupted vì 5 dòng bị drop được bù bằng 5 duplicate; điều này chứng minh cần phối hợp nhiều expectation thay vì chỉ kiểm tra volume.

## 9. Điều học được và hướng cải thiện

1. Observability cần tạo signal có thể hành động, không chỉ lưu log.
2. Freshness là kiểm tra ngữ nghĩa thời gian, khác với schema/completeness checks.
3. Shared benchmark giúp chứng minh quan hệ nhân quả giữa dữ liệu bẩn và RAG degradation.

Nếu có thêm thời gian, tôi sẽ bật Ragas, chạy Gemini judge được cấp quyền và xây dashboard hiển thị pass/fail, stale ratio và degradation theo từng question type.
